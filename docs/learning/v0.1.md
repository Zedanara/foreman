## 0. Три идеи, без которых `ask.py` не понять

### Генератор (`yield`)

Обычная функция возвращает результат один раз через `return` и завершается.
Функция с `yield` — генератор: она отдаёт значение и **замирает** до тех пор,
пока у неё не попросят следующее.

```python
def count():
    yield 1
    yield 2


for x in count():  # получаем 1, потом 2
    print(x)
```

Это удобно для стриминга: ответ модели приходит кусками, и каждый кусок
можно отдать наружу сразу, не дожидаясь конца.

### `async` / `await`

Сетевой запрос — это в основном ожидание. `async def` объявляет **корутину** —
функцию, которая умеет вставать на паузу. `await` говорит: «здесь я жду
сеть, пока можно заниматься другим». Вызов корутины сам по себе ничего не
выполняет, а возвращает объект-задачу. Запускает её **цикл событий** (event
loop), а `asyncio.run(...)` создаёт этот цикл, выполняет корутину до конца
и закрывает цикл.

Для одного вопроса async ничего не ускоряет. Он нужен на будущее: в
Telegram-боте (v0.4) одновременно идут несколько разговоров, и синхронный код
ждал бы модель для одного пользователя, пока остальные висят.

### Асинхронный генератор (`async def` + `yield`)

Это генератор, внутри которого можно делать `await`. Перебирают его через
`async for`. `stream_answer` устроен именно так: он ждёт следующий кусок из
сети (`await` спрятан внутри `async for`) и отдаёт его наружу (`yield`).

## 2. `tests/test_ask.py`

Основные инструменты pytest, которые здесь используются:

- **Тест** — функция с именем `test_*` в файле `test_*.py`. pytest находит их сам.
- **`assert`** — проверка. Если условие ложно, тест падает и pytest показывает обе стороны сравнения.
- **Фикстура** — то, что pytest передаёт в тест по имени параметра. Встроенные фикстуры: `monkeypatch` (временно подменить что-то и вернуть обратно после теста) и `capsys` (перехватить то, что печаталось в stdout/stderr).

## 5. `.pre-commit-config.yaml`

pre-commit запускает проверки **перед каждым `git commit`** на изменённых
файлах. Если проверка падает или что-то исправляет, коммит не создаётся:
нужно посмотреть изменения, сделать `git add` и закоммитить снова.

| Строки | Что делает | Почему так | Если убрать |
|---|---|---|---|
| 1 | Комментарий про `pre-commit install` | Сам файл ничего не включает. Хук ставится в `.git/hooks/` командой, отдельно у каждого разработчика | Новичок создаст файл и будет думать, что проверки работают |
| 3–4 | Репозиторий `pre-commit-hooks`, `rev: v6.0.0` | Точный тег: у всех одинаковые версии хуков | Без `rev` конфиг невалиден |
| 6 | `trailing-whitespace` | Удаляет пробелы в конце строк | Мусорные изменения в diff |
| 7 | `end-of-file-fixer` | Ровно один перевод строки в конце файла (твой `pyproject.toml` его не имел) | `\ No newline at end of file` в diff |
| 8 | `check-yaml` | Проверяет синтаксис YAML, в том числе `ci.yml` | Сломанный отступ в `ci.yml` обнаружился бы только на GitHub |
| 9 | `check-added-large-files` | Не даёт закоммитить большой файл (по умолчанию > 500 КБ) | Модель на гигабайты или дамп базы случайно попадает в историю, и вычищать его оттуда очень больно |
| 10 | `detect-private-key` | Ищет приватные ключи (`-----BEGIN ... PRIVATE KEY-----`) | Ключ уходит на публичный GitHub |
| — | `check-toml` убран | Windows Smart App Control блокирует его `.exe` на твоём ноутбуке. `pyproject.toml` и так парсят uv и ruff при каждом запуске | — |
| 12–14 | `ruff-pre-commit`, `rev: v0.16.10` | Та же версия ruff, что в `uv.lock` | При разных версиях pre-commit и CI могут по-разному отформатировать один файл, и они будут вечно спорить |
| 16–17 | `ruff-check --fix` | Линтер и автоисправление простого (например, порядка импортов) | — |
| 18 | `ruff-format` | Форматирование | Стиль кода расплывётся |

Важно: `ruff-check` идёт **до** `ruff-format`, потому что `--fix` может
изменить код, и форматировать нужно уже финальную версию.

## 6. Docker

В v0.1 Docker не используется: Ollama стоит прямо на Windows, а CI работает
на готовой машине GitHub. Вопрос о Docker встанет, когда бота нужно будет
где-то разворачивать; это решение для будущего ADR.
